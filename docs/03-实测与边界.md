### 2.1 真实推理链路（不是模拟节点）

推理节点是真实的 YOLOv8：Windows 侧 `D:\miniconda3\envs\game\python.exe`，
torch 2.10.0+cu126，RTX 4070 Ti SUPER（CUDA 确认在用，`model device = cuda:0`）；
网关跑在 WSL2，经 vEthernet 网关地址 `172.18.112.1:50051` 访问它。
这里的「跨主机」指 WSL2 虚拟机与 Windows 宿主之间，两者在**同一台物理机**上。

| 项 | 结果 | 说明 |
| --- | --- | --- |
| 端到端 | 12/12 ok，检出 24 个目标（每帧 2 个） | 测试图为真实照片，模型检出 `tie 0.913` + `person 0.889` |
| `gateway_us` | 中位 55 µs（49–83） | 与模拟节点时的 55–99 µs 同一水平 |
| `infer_us` | 中位 15.1 ms（12.9–26.1） | 服务端自报（含 `cv2.imdecode`） |
| `total_us` | 中位 16.8 ms，p95 21.3 | — |
| 网关占比 | 55 µs / 16 777 µs = 0.33% | 这是"瓶颈在推理侧"最直接的证据 |
| 背压（真实推理） | burst 12 帧 → 2 受理 / 10 `OVERLOADED` | 背压与下游是谁无关 |
| 结果一致性 | 经网关返回的框坐标与直接跑 YOLO 逐位一致 | tie 0.913 @ (331.5, 846.4, 121.9, 180.6)；person 0.889 @ (344.0, 507.6, 687.2, 851.7) |

绕过网关直接测量（同一进程，用于对照）：

| 测法 | 中位 | min | max |
| --- | --- | --- | --- |
| `cv2.imdecode` | 2.18 ms | — | — |
| 纯 `YOLO(imgsz=640)`，背靠背 20 次 | 14.27 ms | 9.49 | 18.33 |
| 纯推理，每次间隔 300 ms × 12 | 10.64 ms | 9.36 | 17.27 |
| 纯推理，每次间隔 30 ms × 12 | 9.61 ms | 8.71 | 11.20 |
| 解码 + 推理（对应 T3 口径） | 12.43 ms | — | — |

结论：`12.43 ms`（直接）与 `15.1 ms`（经网关）基本吻合，多出的约 2.7 ms 是
protobuf 反序列化 + 响应组装 + 线程上下文。GPU 低频档爬升不是原因——
有间隔的调用反而更快（9.6–10.6 ms vs 背靠背 14.3 ms）。

注意：这个数字对机器状态非常敏感。同一套链路、同一张图，另一次测量得到
`infer_us` 中位 26.9 ms、`total_us` p95 86.5 ms（最高 84 ms）——
当时 `nvidia-smi` 显示 GPU 利用率 46%，Wallpaper Engine 等桌面应用在占卡。
引用推理耗时时必须说明机器状态，否则数字没有意义。

## 4. 延迟口径

```text
t_start ──parse_us──► t_parsed ──queue_to_grpc_us──► t_grpc_sent
                                                          │
                                        grpc_round_trip_us = infer_us + grpc_transport_us
                                                          ▼
                      t_finish ◄──postprocess_us── t_grpc_recv

gateway_us = parse_us + queue_to_grpc_us + postprocess_us   ← 只算网关自己那三段
total_us   = t_finish - t_start                             ← 端到端
```

- `t_start` 在包头首次可见时记录（`FrameContext` 构造）。跨多次 read 的半包会把等待时间算进 T1。
- `gateway_us` 刻意不包含 gRPC 往返与推理，所以「网关侧 70 µs」这个说法才站得住。
- `grpc_transport_us` 是差值估计（gRPC 往返 − Python 自报推理），含排队与序列化，
  不等于纯网络传输耗时。

## 6. 明确没有验证的（边界）

| 项 | 现状 |
| --- | --- |
| 并发 | 只有单连接。没有多客户端压测、没有 p99、没有长时间稳定性曲线 |
| 真实推理的稳定性 | 真实链路已跑通（见 2.1），但只跑过十几帧；没有长时间连续推理、没有观察 GPU 争用下的长期漂移 |
| 优雅停机 | 无 SIGINT/SIGTERM 处理，`loop()` 是死循环 → `Server::~Server()` 的顺序运行时跑不到 |
| OutputBuffer 上限 | 没有。只发不读的慢客户端能把它撑大 |
| 单测覆盖 | `Epoll` / `Channel` / `AsyncAIEngine` / `Server` / `Acceptor` 无单测 |
| 慢客户端 / 部分写路径 | 未构造出真实的部分写场景，`outputBuffer` 的分支只在代码层面成立。该分支里仍有 `std::cout << ... << std::endl`（与 929 µs 同源的写法），正常负载走不到，所以未体现在上面的数字里 |
| 结果协议 | 手写 JSON，浮点用 `ostream` 默认精度（6 位有效数字），未做定点控制 |

## 7. 引用数字的四条硬规则

1. 说清条件：单机还是跨主机、单连接、WSL2、模拟节点还是真实模型——缺一个都可能被追问打穿。
2. 区分"内存内拷贝"与"网络吞吐"：Buffer 的 GiB/s 是内存内 `append`/`retrieve` 吞吐，
   不等于网卡吞吐，也不等于端到端帧处理能力。
3. 区分"均摊值"与"排队延迟"：线程池那个 `µs/task` 是墙钟时间 ÷ 任务数（均摊吞吐），
   不是单个任务从入队到开始的排队延迟。
4. 说明机器状态：真实推理的中位耗时在同一台机器、同一张图上可以从 15 ms 变到 27 ms、
   p95 到 86 ms。GPU 被桌面应用占用（`nvidia-smi` 显示 46% 利用率）就是其中一次的实测原因。
   报推理耗时必须注明测量时的机器状态，否则这个数字不可复现、也没有比较意义。
