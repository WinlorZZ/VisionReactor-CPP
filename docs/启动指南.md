# 启动指南

这份文档是 `main` 分支的运行流程与动手实验。最短的启动路径在 [README](../README.md)，
这里把它展开写细，并补上排错表和四个可以亲手做的实验。

## 先分清两侧

这个系统由两侧组成，它们在各自的进程里跑，不要求在同一台机器上。

| | 网关侧 | 推理侧 |
| --- | --- | --- |
| 是什么 | 本仓库编译出来的 C++ 程序 `server` | Python 程序 `Pserver.py` 或 `dummy_server.py` |
| 跑在哪 | 必须是 Linux 或 WSL，它依赖 `epoll` | 有 Python 就行；可以在 WSL 里，也可以在 Windows 上用 GPU |
| 做什么 | 收帧、拆包、转发、逐帧计时、把结果发回 | 解码图像、跑模型、报告自己的推理耗时 |
| 之间怎么连 | —— | gRPC，默认端口 50051 |

本文按侧分节，**一节里只有这一侧的命令**。要开三个终端：

| 终端 | 属于哪一侧 | 后面在哪一节 |
| --- | --- | --- |
| 终端 1 | 网关侧（Linux 或 WSL） | 「网关侧：编译与启动」 |
| 终端 2 | 推理侧（WSL 或 Windows） | 「推理侧：环境与启动」 |
| 终端 3 | 客户端（跟网关同一台机器） | 「客户端：两种发帧方式」 |

`parse_us`、`queue_to_grpc_us`、`postprocess_us` 和 `gateway_us` 都是网关侧的；
`infer_us` 是推理侧自报的，网关只是把它转述出来；`total_us` 是端到端的，跨了两侧。

## 完整版比精简版多什么

| 多出来的 | 现状 |
| --- | --- |
| **WebSocket 直连** | 写在 `src/Connection.cpp` 里（握手、解掩码、帧封装），和 TCP 共用同一条流水 |
| **浏览器演示** | `web_demo/`（`index.html` / `app.js` / `styles.css`），上传视频、抽帧、画检测框、显示分段延迟 |
| **H.264 解复用模块** | `include/h264_demuxer.h` + `src/h264_demuxer.cpp` + 单测。注意：**它没有接入推理主链路**——`Connection::processH264Nalus()` 没有任何调用点，跑起来什么都不会发生 |
| `doc/` 下的设计与验证记录 | 类图、数据流、协议、实测记录、学习笔记 |

## 网关侧：编译与启动

以下命令全部在终端 1 里执行。

### 安装系统依赖

完整版的 `CMakeLists.txt` 里有 `find_package(OpenSSL REQUIRED)` 和 `find_package(OpenCV REQUIRED)`，
所以除了 gRPC 和 Protobuf，还要这两个：

```bash
sudo apt install -y build-essential cmake libgrpc++-dev protobuf-compiler-grpc \
  libprotobuf-dev protobuf-compiler libssl-dev libopencv-dev
```

顺带说明：**OpenCV 被声明为必需，但代码里没有任何 `cv::` 调用**（唯一那句 `#include <opencv2/opencv.hpp>`
是历史遗留）。装它只是为了满足 CMake 的检查。

### 解决 googletest

精简版会先找系统安装的 GTest，完整版**没有** `find_package(GTest)`，只走 `FetchContent`，
也就是必须从 GitHub 下载。两种办法：

有网络（或配了代理）时直接构建即可：

```bash
export https_proxy=http://<代理地址>:<端口>
export http_proxy=$https_proxy
make build
```

注意，**CMake 不读 git 的代理配置**：它下载 GTest 用的是 libcurl，只看 `https_proxy` 和
`http_proxy` 环境变量。所以会出现 git 能克隆、CMake 却失败的情况，配置阶段卡大约 86 秒后报
`Could not resolve host: github.com`。

不想联网就自己调 cmake，把本地 GTest 源码传进去：

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug \
  -DFETCHCONTENT_SOURCE_DIR_GOOGLETEST=/path/to/googletest-src
cmake --build build --parallel
```

注意，完整版的 Makefile 只有 `configure` / `build` / `test` / `bench` / `clean` 五个目标，
**没有 `release`，也不接受 `GTEST_SRC=`**——离线构建只能像上面这样直接调 cmake。

### 编译并跑测试

```bash
make build
```

配置阶段会打印找到的库：

```text
-- Found OpenSSL: /usr/lib/x86_64-linux-gnu/libcrypto.so (found version "3.0.13")
-- Found OpenCV: /usr (found version "4.6.0")
```

编译结束不应有 error，16 核机器上大约 25 秒。产物是 `build/server`（Debug 构建）。

跑单元测试：


### 启动网关

推理节点的地址填在命令行上：

```bash
# 推理侧和网关在同一台机器上
./build/server 127.0.0.1:50051

# 推理侧在本机的 Windows 侧（WSL 连 Windows 宿主）
./build/server $(ip route | awk '/^default/{print $3}'):50051

# 推理侧在另一台机器上
./build/server 192.168.1.50:50051
```

第二种那个地址是 WSL 的 vEthernet 网关，也就是 Windows 宿主，本机实测是 `172.18.112.1`，
只在同一台物理机上有意义。第三种要填那台机器的局域网地址，在推理侧那台机器上用
`ipconfig | Select-String 'IPv4'` 查，并且要放行 `50051` 入站。

这里只用了地址，所以推理节点还没启动也没关系。

注意，**网关启动后什么都不打印**。它没有「监听于……」这样的横幅，构造完就直接进 `epoll_wait`，
只在有事件时才有输出。要确认它在监听：

```bash
ss -ltnp | grep 8888
```

默认监听 `127.0.0.1:8888`，浏览器演示和 TCP 客户端都连这个端口。这个终端先留着别关。

## 推理侧：环境与启动

在终端 2 里执行。需要 torch 和 ultralytics，**别装进 `base`**，先建隔离环境：

```bash
conda create -n vision python=3.10 -y
conda activate vision
pip install grpcio grpcio-tools protobuf numpy opencv-python torch ultralytics
```

这一步会连带拉 torch 和一堆 CUDA 运行库，大约 2 到 3 GB。用 venv 也可以，
把 `conda create` 换成 `/usr/bin/python3 -m venv .venv && source .venv/bin/activate`。

装完检查一下：

```bash
python -c "import grpc, grpc_tools, torch, ultralytics; print('OK', torch.cuda.is_available())"
```

然后启动节点。**必须先切到 `python_ai` 目录**，`Pserver.py` 里 `YOLO('yolov8n.pt')`
用的是相对路径：


- **必须带 `-u`**。不加的话 Python 输出被缓冲，窗口一片空白，看起来像没启动。
- **模型权重不入库**，首次运行会由 ultralytics 自动下载 `yolov8n.pt`（约 6 MB，需要网络）。
  要离线就先把权重放进 `python_ai/`。

## 客户端：两种发帧方式

两条路**共用同一条后端流水**，区别只在帧从哪里来、用什么传输：

| | 演示一 | 演示二 |
| --- | --- | --- |
| 帧来源 | 磁盘上的一张图片（仓库自带 `testdata/test.jpg`） | `<video>` 按设定帧率抽帧（仓库自带 `testdata/test.mp4`） |
| 传输 | 原始 TCP（4 字节大端长度 + JPEG） | WebSocket（二进制帧，带掩码） |
| 适合看什么 | 协议闭环、单帧的完整 JSON 与探针 | 实时叠加、分段延迟与背压表现 |
| 用什么跑 | `tools/image_client.py`（只用标准库） | `web_demo/index.html` + `app.js` |

### 演示二：浏览器实时视频（WebSocket）

打开 `web_demo/index.html` 就行，或者起一个静态服务器：

```bash
cd ~/VisionReactor-CPP/web_demo
python3 -m http.server 8080
# 然后浏览器访问 http://127.0.0.1:8080
```

页面默认连接：

```text
ws://127.0.0.1:8888
```

使用流程：

1. 点「连接」。这一步完成浏览器到 C++ 网关的 WebSocket 握手（服务端会回 `101 Switching Protocols`）。
2. 选择一个视频文件。仓库自带了 `testdata/test.mp4`（H.264，640x480）；浏览器能播的格式都可以（MP4/H.264、WebM、MOV 等），页面上能看见画面就说明能抽帧。
3. 点「播放」。前端按设定的 FPS 从 `<video>` 抽帧成 JPEG，用**二进制帧**发给网关。帧率滑块范围 1–20，默认 8。
4. 页面在视频上叠加检测框，右侧实时显示 `Total`、`Gateway`、`gRPC`、`Infer`、`Objects`、
   `In flight`。

关于这条路的几个事实：

- **客户端发的是二进制帧（opcode 0x2）且必须加掩码**，服务端回的是**文本帧（opcode 0x1）**，
  内容是 UTF-8 的 JSON。客户端不加掩码会被直接断开。
- 网关侧拆包之后的所有逻辑（在途上限、线程归属）与 TCP 路径**完全共用**。
- 抽帧画布按视频**原生分辨率**建立，JPEG 质量固定 0.72，所以分辨率越高每帧越大，720p 左右最合适。
- `In flight` 显示当前在途请求数，每连接上限是 2。页面收到 `OVERLOADED` 时会**自动把帧率调低一级**，
  这就是背压契约。
- 浏览器一次只连一个 WebSocket，所以它看到的 `frame_id` 是全局单调递增的追踪号。
- 浏览器解不了的格式**不会报错**：`videoWidth` 会一直是 0，表现为点了「播放」但 `Frame` 一直是 `-`。
  遇到这个先怀疑视频格式，而不是网关。

要脚本化验证（不开浏览器）也能做：按上面那套协议手写一个最小的客户端即可——
握手用 `Sec-WebSocket-Key`，之后发带掩码的二进制帧、收文本帧。

## 看一眼返回的 JSON

判断一次调用是否正常，看三件事：`ok` 是 `true`；`gateway_us` 在几十到几百微秒之间；
`total_us` 主要被 `infer_us` 占掉。

`detections` 里每一项是一个检测框，`x` / `y` 是中心点，`w` / `h` 是宽高，
坐标都是原图像素；`class` 取自模型自己的 `names` 表。

失败响应是另一种形状：多一个 `code` 字段，`timing` 只有三个字段，`detections` 为空。
各字段的完整含义、计算口径与错误码见 [项目说明](项目说明.md) 的协议一节。

## 常见问题

网关侧：

| 现象 | 原因与处理 |
| --- | --- |
| `make: *** No rule to make target 'release'` | 完整版没有这个目标。用 `make build`，产物在 `build/server` |
| `find_package(OpenCV)` 或 `find_package(OpenSSL)` 失败 | 少装了 `libopencv-dev` / `libssl-dev` |
| 配置阶段卡约 86 秒后报 `Could not resolve host` | CMake 拉 GTest 要联网，而且不读 git 的代理配置。设 `https_proxy`，或自己调 cmake 传 `-DFETCHCONTENT_SOURCE_DIR_GOOGLETEST=` |
| 网关什么都不打印 | 它本来就不打印。用 `ss -ltnp \| grep 8888` 确认在监听 |
| 返回 `code` 是 `RPC_FAILED` | 推理节点没启动，或者网关启动时填的地址不对 |
| 返回 `code` 是 `OVERLOADED` | 每连接在途请求超过 2。这是正常工作，让发送端放慢 |
| 连上了之后每帧都回 `OVERLOADED` | 推理卡住没返回，在途额度不归还（完整版没有 RPC 截止时间）。重启推理节点即可 |
| 想跑基准却没有 `build-release/` | Makefile 没有 release 目标，自己调 cmake 指定 `-DCMAKE_BUILD_TYPE=Release` |

推理侧：

| 现象 | 原因与处理 |
| --- | --- |
| 节点看起来没启动 | 输出被缓冲了，要加 `-u` |
| 报找不到 `yolov8n.pt` | 没在 `python_ai` 目录下运行；首次运行还需要网络下载权重 |
| 首次启动卡很久 | 在下 `yolov8n.pt`（约 6 MB）和加载 CUDA，属正常 |
| `pip install` 卡住 | pip 也只看环境变量，需要代理时先设 `HTTPS_PROXY` |

浏览器：

| 现象 | 原因与处理 |
| --- | --- |
| 点「连接」没反应 | 网关没启动，或者端口不是 8888。看浏览器控制台的报错 |
| 连上了但一直没有框 | 视频没点「播放」；或推理节点没通（`In flight` 停在 2，之后每帧都回 `OVERLOADED`）；或浏览器解不了这个视频格式（`Frame` 一直是 `-`） |
| `In flight` 长期是 2 | 推理比两秒还慢。页会自动降帧率，但根本原因是推理侧太慢 |
| 通过 `http.server` 打开却连不上 | 页面连的是 `ws://127.0.0.1:8888`（网关），跟静态服务器的 8080 端口不是一回事 |

## 动手实验

上面的流程把链路跑通了，下面四个实验接着做。每个实验只动一侧，改动很小，
但要观察到的东西都能直接回答一个问题。做完之后，「我知道」就变成「我验证过」。


三个终端还是前面那三个：

| 终端 | 属于哪一侧 | 跑着什么 |
| --- | --- | --- |
| 终端 1 | 网关侧（Linux 或 WSL） | `build/server` |
| 终端 2 | 推理侧（WSL 或 Windows） | `dummy_server.py` |
| 终端 3 | 客户端（跟网关同一台机器） | 下面这些命令 |

实验脚本在仓库的 `tools/` 里，都只用标准库，`python3` 直接能跑。

四个实验分别动哪一侧：

| 实验 | 动哪一侧 | 看什么 |
| --- | --- | --- |
| 一：半包 | 客户端（终端 3） | 终端 1 里的 `parse_us` |
| 二：去掉 tie | 网关侧（终端 1）改一行并重建，客户端（终端 3）断开 | 终端 1 里的 ASan 报告 |
| 三：让推理挂住 | 推理侧（终端 2）改参数，客户端（终端 3）发帧 | 客户端拿到的错误码 |
| 四：持续发帧 | 客户端（终端 3） | 吞吐与错误码分布 |

做实验时别让机器同时跑别的重活。推理耗时对这一点很敏感，同一张图、同一条链路，
换个时刻能从 15 毫秒变到 70 毫秒；那样观察到的数字就没法归因了。

### 实验一：半包

要观察的是网关侧怎么处理「长度头和包体分两次到达」。

客户端（终端 3）把一帧拆成两次 `send`，中间停半秒。这个脚本是纯标准库写的，不需要 grpcio：

```bash
python3 tools/half_packet_client.py --image testdata/test.jpg --gap 0      # 对照组，一次发完
python3 tools/half_packet_client.py --image testdata/test.jpg --gap 0.5    # 实验组，拆成两次
```

发完回终端 1 看网关探针：

```text
Frame: 1  ├─ T1 (TCP Parse) :   0.03 ms     ← 一次发完
Frame: 2  ├─ T1 (TCP Parse) : 509.21 ms     ← 拆成两次，等待被算进 T1
```

两组都是 `ok=true`：

| 组 | `parse_us` | 客户端总耗时 |
| --- | --- | --- |
| 对照组，`--gap 0` | 33 微秒 | 33.7 毫秒 |
| 实验组，`--gap 0.5` | 509210 微秒，约 509 毫秒 | 532.1 毫秒 |

`parse_us` 是从 `t_start` 到 `t_parsed`，而 `t_start` 在包头首次可见时打点。
如果半包时消费了游标，第二段数据到达时会被当成新包头解析，长度校验失败，连接会被关掉。
现在看到 509 毫秒而且帧正常完成，就说明 `FrameContext` 跨读保留、游标没动。

顺带这也说明了 `parse_us` 的口径边界：它包含半包等待时间。引用它的稳态值（约 4 微秒）时，
前提是整帧一次到达。

### 实验二：去掉 tie 会怎样

这个实验只改网关侧的一行代码，客户端只需要「发一帧之后立刻断开」。

网关侧（终端 1），先按 Ctrl-C 停掉原来的网关，把那行注释掉：

```cpp
// channel->tie( shared_from_this() );
```

然后构建一个带 ASan/UBSan 的版本并启动。完整版的 Makefile 没有 sanitizer 目标，直接调 cmake：

```bash
cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_FLAGS="-fsanitize=address,undefined -fno-omit-frame-pointer -g" \
  -DFETCHCONTENT_SOURCE_DIR_GOOGLETEST=/path/to/googletest-src
cmake --build build-asan --parallel
ASAN_OPTIONS=detect_leaks=0 ./build-asan/server 127.0.0.1:50051
```

`-DFETCHCONTENT_SOURCE_DIR_GOOGLETEST=` 只是为了不联网；有网络时去掉它，让 CMake 自己下载。
16 核机器上配置约 5 秒、编译约 15 秒。

客户端（终端 3），发一帧之后用 RST 断开，不等回复：

```bash
python3 - <<'EOF'
import socket, struct
jpeg = open('testdata/test.jpg', 'rb').read()
s = socket.create_connection(('127.0.0.1', 8888), 5)
s.sendall(struct.pack('>I', len(jpeg)) + jpeg)
s.setsockopt(socket.SOL_SOCKET, socket.SO_LINGER, struct.pack('ii', 1, 0))  # close 时发 RST
s.close()
EOF
```

终端 1 里立刻出现报告，位置就在读事件里：

```text
==16827==ERROR: AddressSanitizer: heap-use-after-free on address 0x50f000000cf0
    #0 Connection::handleReadEvent() src/Connection.cpp:86
freed by thread T0 here:
    #0 operator delete(void*, unsigned long)
    #1 std::_Sp_counted_ptr_inplace<Connection, std::allocator<void>, ...>::deallocate
SUMMARY: AddressSanitizer: heap-use-after-free src/Connection.cpp:86 in Connection::handleReadEvent()
```

释放栈里出现 `_Sp_counted_ptr_inplace<Connection>`，说明这个对象是被 `shared_ptr` 释放的：
`conns.erase()` 之后引用计数归零，而事件回调还在用它的成员。

而同一份构建下，单元测试不会失败：

```bash
ctest --test-dir build-asan -R connection_test
```

```text
100% tests passed, 0 tests failed out of 1
```

因为它没有真实的 epoll 事件，走不到「回调中途对象被删除」这条路径。
这是本仓库里「单测通过不等于正确」最直接的一个例子。

做完记得把那行改回来，重新构建。

### 实验三：让推理挂住

这个实验要动推理侧和客户端两侧，顺序是先让推理变慢、再连发。反面对照要改网关侧。

推理侧（终端 2），按 Ctrl-C 停掉原来的节点，把等待时间改大重启：

```bash
cd ~/VisionReactor-CPP/python_ai
python3 -u dummy_server.py --port 50051 --latency-ms 60000 --boxes 2
```

客户端（终端 3）连发十帧：

```bash
python3 tools/batch_client.py --image testdata/test.jpg --frames 10 --mode burst
```

前两帧被受理，其余立刻回 `OVERLOADED`。**那两帧就再也不会回来了**：完整版没有 RPC 截止时间，
推理不返回，额度就不归还——之后再发新帧仍然全部是 `OVERLOADED`，直到重启推理节点或客户端重连。

这正好是个对比分支的好例子。切到 `slim` 跑同一实验：它给 RPC 设了 `kRpcDeadlineMs = 2000`，
两秒后那两帧以 `TIMEOUT` 结束、额度归还，连接恢复正常。

### 实验四：持续发帧

前三个实验都只发一两帧。要持续发，用 `batch_client.py`，它有两种模式：

| 模式 | 行为 | 用来看什么 |
| --- | --- | --- |
| `--mode seq` | 发一帧等一帧 | 稳态延迟分布与吞吐。在途数永远是 1，不会丢帧 |
| `--mode burst` | 一次连发 N 帧再收 | 背压：超过每连接在途上限的帧会被拒 |

客户端（终端 3）：

```bash
python3 tools/batch_client.py --image testdata/test.jpg --frames 20 --mode seq
python3 tools/batch_client.py --image testdata/test.jpg --frames 10 --mode burst
```

`seq` 模式会打出每个时间段的 min / 中位 / p95 / max 和 fps；`burst` 模式的 `error_codes`
里会出现 `OVERLOADED`。

注意，`seq` 模式**没有限速**，它拿到一帧回复就立刻发下一帧，所以实际帧率等于
「1 除以单帧往返时间」。想固定帧率或者无限持续，得自己在循环里加 `sleep`，
`batch_client.py` 没有这个参数。

还要注意，别拿它去压一个本来就很慢的推理节点。客户端的截止时间是 2 秒，一到点就放弃这一帧，
但**推理侧不会因此停下**，它还在算。如果推理比 2 秒慢，`seq` 模式每发一帧都会留下一个
「已被放弃但仍在计算」的请求，越堆越深，之后每一帧都超时。我们在这台机器上撞见过：
一边有别的任务占着 GPU，`seq 20` 帧的结果是 20 次失败、墙钟 40 秒：
没有截止时间时，卡住的推理会把在途额度一直占着，后面的帧只能被拒。
遇到这种情况，重启推理节点就清空了。

### 实验做完了怎么读结果

三种错误码分别说明问题在哪一侧，见 [项目说明](项目说明.md) 的协议一节。
做实验时先看错误码落在哪一行，就能直接确定该查哪一侧，不用两头猜。

小结：

- 半包不消费游标，代价是 `parse_us` 把等待时间也算进去。
- 去掉 `tie` 会真的 use-after-free，而且单元测试测不出来。
- 在途上限和截止时间分别防堆积和防额度泄漏；截止时间只保护网关，不会让推理侧停下。
- 持续发帧用 `seq` 模式，帧率由单帧往返时间决定；要固定帧率得自己加 sleep。
