# 带你过一遍

这一篇按理解的顺序走一遍项目：先看它整体在做什么，再顺着一次请求走完整条链路，
然后是内存与资源管理，最后是设计和取舍。读完之后我们会知道每个关键决定为什么这么定，
以及哪些地方是 knowingly 欠着的。

`docs/01` 到 `docs/04` 是参考手册，按主题组织，适合回头查；这一篇适合从头读一遍。
全篇大约两到三小时。想先跑起来，看 [00-开始项目.md](00-开始项目.md)。

## 全景

### 这个项目做什么

一句话：把一张图收进来，原样转给 Python 做目标检测，把检测框写成 JSON 发回去。

它自己不解码、不 resize、不识别、不存储、不训练，真正的计算全在 Python 那边。
它自己的业务逻辑只有三条防线：帧长度校验、每连接的实例上限、每个 RPC 的截止时间。

### 定位

这是一个实验性项目。方向是实时画面检查，也就是屏幕或相机画面实时检测并叠加标记。
本仓库是那条路的第一步，先把「帧进来、异步送推理、结果回来」这条管道和它的延迟搞清楚。
捕获和叠加显示都还没做。

### 组件与线程

```text
                     ┌──────────────── 一个 EventLoop 线程 ────────────────┐
客户端 ──TCP──►      │  epoll_wait ──► Channel::handleEvent               │
                     │      ├─ Acceptor 的可读 → accept 新连接             │
                     │      ├─ Connection 的可读 → 收帧 → 拆包 → 发 RPC    │
                     │      ├─ Connection 的可写 → 排空 outputBuffer       │
                     │      └─ eventfd 可读 → 执行别人投递进来的闭包        │
                     └───────┬───────────────────────────▲────────────────┘
                             │ 发起异步 RPC               │ runInLoop 回投
                             ▼                           │
                  ┌── CQ 线程 ──┐              ┌── ThreadPool（4 线程）──┐
                  │ cq_.Next()  │──add 任务──► │ JSON 序列化 + 打探针日志 │
                  └─────────────┘              └────────────────────────┘
                             ▲
                             │ gRPC（异步）
                             ▼
                     Python YOLOv8（另一个进程，可以跨机器）
```

有三件事需要先记住。

第一，只有一个 Reactor 线程。它既读又写又拆包，所以这些操作必须足够快。

第二，Worker 和 CQ 线程都不碰 socket。它们想回数据，必须用 `runInLoop` 把闭包投回 Reactor。

第三，Worker 池只干轻活，也就是 JSON 序列化和日志。拆包不在这里，原因后面讲取舍时会说明。

### 两侧

上面的图只画了网关侧。推理侧是独立的 Python 进程，通过 gRPC 与 `AsyncAIEngine` 相连，
可以在同一台机器上，也可以在另一台机器上。`gateway_us` 属于网关侧，`infer_us` 由推理侧自报，
`total_us` 跨两侧。分清这一点，后面所有数字才有意义。

## 启动与运行时

### 启动流程

`main.cpp` 只有 23 行，内容就是组装：

```cpp
signal(SIGPIPE, SIG_IGN);              // 防止往已关闭的 socket 写时进程被杀
std::string ai_target = "127.0.0.1:50051";
if (argc >= 2) ai_target = argv[1];    // AI 地址可以传参
EventLoop loop;                        // 建事件循环，栈上
Server server(&loop, ai_target);       // 建服务器
loop.loop();                           // 阻塞在这里
```

`Server` 的构造函数里做三件事：

```cpp
acceptor    = new Acceptor(loop);                    // 监听并注册 accept 回调
threadPool  = new ThreadPool(4);                     // 固定 4 个工作线程
aiengine    = std::make_unique<AsyncAIEngine>(gchannel, threadPool);
```

接着 `Server` 把三个回调绑到 `Connection` 上。这三个回调是理解全局的钥匙：

| 回调 | 什么时候触发 | 做什么 |
| --- | --- | --- |
| `handleNewConnection` | accept 到新连接 | 建 `Connection`，放进 `conns`，绑下面两个回调 |
| `handleOnMessage` | 读到一个完整帧 | 调 `conn->business(engine)`，就在 EventLoop 线程里 |
| `handleDeleteConnection` | 连接要销毁 | 从 `conns` 里 erase，这一步才真正释放 `Connection` |

### 运行时只有三类事件

`loop.loop()` 起来之后，程序所有时间都花在 `epoll_wait` 上，被唤醒只有三个原因：

1. 监听 fd 可读，来了新连接，走 `Acceptor::acceptNewConnection`，循环 accept 到 `EAGAIN`。
2. 连接 fd 可读或可写，走 `Connection::handleReadEvent` 或 `handleWriteEvent`。
3. `eventfd` 可读，说明有别的线程投递了闭包，走 `doPendingFunctors` 执行它们。

第三条是跨线程协作的全部机制。没有它，Worker 和 CQ 线程就没法安全地碰任何连接状态。

### 网关的六项功能

| 功能 | 在哪 |
| --- | --- |
| TCP 收帧和长度前缀拆包，含半包 | `Connection::business` |
| 异步转发给推理服务，不阻塞 Reactor | `AsyncAIEngine::AnalyzeFrameAsync` |
| 背压：每连接在途上限 2，超了回 `OVERLOADED` | `Connection::submitImageInLoop` |
| 超时：每个 RPC 两秒截止，超了回 `TIMEOUT` 并归还额度 | `AsyncAIEngine::kRpcDeadlineMs` |
| 结果回传和 JSON 序列化，含转义 | `ResponseSerializer` |
| 逐帧六段延迟打点 | `LatencyProfiler` 与 `FrameContext` |

### 一帧的生命周期

```text
到达 → 拆包 → 发 RPC → 等（不占线程）→ CQ 收到 → 序列化 → 回投 Reactor → 写出
 T1     T1     T2                         T4          T4                    ↑
                    └──── gRPC 往返 + Python 推理（不占网关线程）────┘
```

关键是中间那一段：从发 RPC 到收到结果之间，网关一个线程都没占住。这就是异步的意义。

## 数据链路

### 线协议

请求是四字节大端长度加 body，body 就是原始 JPEG 字节，长度必须大于 0 且不超过 10 MiB：

```text
┌──────────────┬────────────────────────────┐
│ 4 字节大端长度 │ body（原始 JPEG 字节）       │
└──────────────┴────────────────────────────┘
```

响应格式相同，只是 body 变成了 UTF-8 的 JSON 文本。

解析用 `Buffer::peekInt32()` 读长度（内部会做 `ntohl`），再用 `Buffer::retrieve(4)` 丢弃包头；
封包用 `ResponseSerializer::frameTcpPayload()`，它就是 `htonl(len)` 拼上 json。

### 全路径 13 步

下表把一次请求拆成十三步，每一步都标了它在哪一侧、在哪个线程。

| 步 | 侧 | 在哪 | 线程 | 做了什么 |
| --- | --- | --- | --- | --- |
| 1 | 网关侧 | `Acceptor::acceptNewConnection` | EventLoop | epoll 报监听 fd 可读，循环 accept 到 `EAGAIN`，每个新 fd 设非阻塞 |
| 2 | 网关侧 | `Server::handleNewConnection` | EventLoop | `make_shared<Connection>`，绑三个回调，放进 `conns[fd]` |
| 3 | 客户端 | —— | 客户端 | 发出四字节长度加 JPEG，进内核发送缓冲 |
| 4 | 网关侧 | `Connection::handleReadEvent` | EventLoop | epoll 报可读，经 `Channel::handleEvent` 进到这里 |
| 5 | 网关侧 | `Buffer::readFd` | EventLoop | `readv` 读两块内存，循环读到 `EAGAIN` |
| 6 | 网关侧 | `Connection::business` | EventLoop | `peekInt32` 校验长度，数据够一整帧就取出，打 `t_parsed` |
| 7 | 网关侧 | `Connection::submitImageInLoop` | EventLoop | 检查在途数小于 2，`++in_flight`，调 `AnalyzeFrameAsync` |
| 8 | 网关侧 | `AsyncAIEngine::AnalyzeFrameAsync` | EventLoop | 填请求体、设两秒截止、`PrepareAsync` 加 `StartCall`、登记 tag、`Finish()` |
| 9 | 网关侧 | gRPC 内部 | gRPC 自己的线程 | 序列化 protobuf 并发给 Python |
| 10 | 推理侧 | `Pserver.py` 或 `dummy_server.py` | Python 进程 | 解码、推理、返回 `FrameResponse`，含自报的推理耗时 |
| 11 | 网关侧 | `AsyncAIEngine::AsyncCompleteRpc` | CQ 线程 | `cq_.Next()` 拿到 tag，从 `active_calls_` 取出并 erase，投给线程池 |
| 12 | 网关侧 | Worker 里的 lambda | ThreadPool | 打 `t_grpc_recv` 和 `t_finish`，序列化成 JSON，调 `completeAnalysis` |
| 13 | 网关侧 | `completeAnalysis` → `runInLoop` → `sendInLoop` | 回投到 EventLoop | 归还额度，`write()` 直写，写不完就转 `outputBuffer` 并注册 `EPOLLOUT` |

第十三步的线程切换值得单独注意：Worker 只做 JSON 序列化，真正的 `write()` 由 EventLoop 线程执行。

第十步是唯一的推理侧。两侧可以在不同机器上，例如网关在 WSL、推理在 Windows 上用 GPU
（本机的 Windows 侧，或另一台机器），
中间的 gRPC 那一步就是真正的跨主机边界。

### Buffer 游标的变化

初始时两个游标都在 8，也就是预留头之后。假设收到 `[4B=1000][1000 字节 JPEG]`，分两次到达。

第一次到达 600 字节：

```text
[8 字节头][600 字节数据][空...]
 r=8        w=608

peekInt32() 读 r 到 r+4，得到长度 1000，读游标不动
readableBytes()=600 < 4+1000，break，退出循环，等下一次可读
```

第二次到达 404 字节：

```text
[8 字节头][600][404][空...]
 r=8              w=1012

readableBytes()=1012 >= 1004，数据够了
retrieve(4)            丢弃包头，r=12
retrieveAsString(1000) 拷出整帧，r=1012，w=1012
循环继续时 readableBytes()=0 < 4，退出
```

半包时一行都不消费，读游标不动，靠下一轮从同一位置重看同一个头。这也是为什么
`parse_us` 在半包场景会包含等待时间，实验一会看到这一点。

### 返回的 JSON

成功时是这样：

```json
{"frame_id":7,"ok":true,"error":"",
 "timing":{"total_us":21600,"gateway_us":70,"parse_us":4,
           "queue_to_grpc_us":12,"grpc_round_trip_us":21400,
           "grpc_transport_us":1300,"infer_us":20100,"postprocess_us":54},
 "detections":[{"class":"weld_seam","confidence":0.91,"x":120.5,"y":88.0,"w":64.0,"h":48.0}]}
```

失败时（`OVERLOADED`、`TIMEOUT`、`RPC_FAILED` 或协议错误）是这样：

```json
{"frame_id":0,"ok":false,"error":"Too many in-flight frames; slow down the sender.",
 "code":"OVERLOADED",
 "timing":{"total_us":0,"gateway_us":0,"infer_us":0},"detections":[]}
```

`timing` 里三个派生量都是减法：

```text
grpc_round_trip_us = t_grpc_recv - t_grpc_sent
grpc_transport_us  = grpc_round_trip_us - infer_us      含排队与序列化，是差值估计
gateway_us         = parse_us + queue_to_grpc_us + postprocess_us
```

### 三条容易走错的路径

半包，也就是数据分多次到达时，不消费任何字节，`FrameContext` 跨读保留在 `current_frame_ctx_` 里。

在途数已经到 2 时，当场回 `OVERLOADED`，`frame_id` 填 0。填 0 是因为这一帧还没被分配 TraceID，
它根本没进推理流程。这里不排队。

推理超过两秒时，CQ 以 `DEADLINE_EXCEEDED` 结束这次调用，走的是和失败完全相同的代码路径，
也就是 `AsyncCompleteRpc` 的错误分支，所以 `--in_flight_requests_` 一定会被执行到。
错误码在客户端侧被映射成 `TIMEOUT`，与普通的 `RPC_FAILED` 区分开。

## 内存与资源管理

这一部分是这个项目最值得讲的地方。异步网络程序的 bug 大多不是逻辑错，而是生命周期错。

### 所有权

| 对象 | 谁持有 | 引用类型 | 说明 |
| --- | --- | --- | --- |
| `EventLoop` 和 `Server` | `main` 的栈 | 值 | 生命周期等于进程 |
| `Acceptor` 和 `ThreadPool` | `Server` | 裸指针加 new/delete | 本该用 `unique_ptr`，见后面「如果重做」 |
| `AsyncAIEngine` | `Server` | `unique_ptr` | —— |
| `Connection` | `Server::conns` | `shared_ptr`，唯一的强引用 | 以 fd 为键 |
| `Connection` 的临时保命引用 | `Channel::tie_` | `weak_ptr` | 只在事件回调期间提升 |
| 回调用到的 `Connection` | 各个 lambda | `weak_ptr` | 见「回调里捕获什么」 |
| `AsyncClientCall` | `AsyncAIEngine::active_calls_` | `shared_ptr` | 以 tag 为键 |
| `FrameContext` | 从 `current_frame_ctx_` 一路传到回调用 | `shared_ptr` | 跨线程、跨阶段共享 |
| `Socket`、`Channel`、两个 `Buffer` | `Connection` | 裸指针加 delete | 析构顺序有讲究 |

要记住的是：`Connection` 的强引用只有一处，就是 `Server::conns`。其他地方都是弱引用。

### 连接什么时候销毁

有三个触发点：

```text
对端正常关闭或读出错  → handleClose()，置 kDisconnecting
协议错误（长度不合法）  → handleClose()
写失败（不是 EAGAIN）  → handleClose()
```

`handleClose()` 之后分两种情况。如果 `outputBuffer` 已经空了，立刻回调
`deleteConnectionCallback`，`Server::conns.erase(fd)`，引用计数归零，析构。
如果 `outputBuffer` 还有残留，就保留 `EPOLLOUT` 把数据发完，等 `handleWriteEvent` 排空后才触发删除，
也就是优雅挥手。

还有一个没列在表里的触发点：客户端直接发 RST。这时 `readv` 返回 0 或报错，走的就是第一种情况。

### 弱引用 guard

看 `Channel::handleEvent` 的骨架：

```cpp
auto guard = tie_.lock();      // 提升成临时 shared_ptr，计数加一
if (guard) {                   // 对象还活着才继续
    handleEventCallback();     // 回调内部可能触发删除，把 conns 里的最后一个 shared_ptr 抹掉
}                              // guard 析构，这时对象才真正死亡
```

没有这个 `guard` 会怎样？断连时 `handleClose()` 触发删除回调，`conns.erase()` 之后引用计数归零，
于是 `Connection` 在 `handleReadEvent()` 还没返回的时候就被析构了，回到 `handleEvent` 继续用成员变量，
就是 use-after-free。

为什么必须是 `weak_ptr` 而不是 `shared_ptr`？如果 `Channel` 持有强引用，`conns.erase()` 之后就永远
没人能析构它，连接泄漏。弱引用不改变计数，只是借命。

这个错误实测过：去掉 `tie` 那一行，用 ASan 构建，跑一个发完就断的客户端，直接报
`heap-use-after-free`。值得注意的是 `connection_test` 里的相关用例不会失败，因为它没有真实的
epoll 事件，走不到这条路径。这是「单测通过不等于正确」的一个好例子，实验二会重现它。

### Buffer 的内存行为

```cpp
static const size_t kCheapPrepend = 8;     // 头部预留
static const size_t kInitialSize  = 1024;  // 初始容量
std::vector<char> buffer_;
size_t readerIndex_, writerIndex_;         // 双游标
```

扩容函数 `makeSpace` 只有两个分支：

```cpp
if (writableBytes() + prependableBytes() < len + kCheapPrepend) {
    buffer_.resize(writerIndex_ + len);      // 真实扩容，向 OS 申请
} else {
    // 内部搬移：把可读数据整体平移到 kCheapPrepend 处
    std::copy(begin() + readerIndex_, begin() + writerIndex_, begin() + kCheapPrepend);
    readerIndex_ = kCheapPrepend;
    writerIndex_ = kCheapPrepend + readable;
}
```

判断式左边是尾部可写空间加头部已读死区。因为死区可以回收，稳态流量下走的是搬移分支，
一次 `memmove`，不向 OS 申请，所以缓冲区在稳定流量下容量稳定。
它也不会收缩，`vector` 的容量只增不减。

八字节预留头需要单独说明一下。它沿袭自 muduo，本来是给「往头部前置长度前缀」用的。
但当前代码里既没有 `prepend` 方法也没有调用者，长度前缀是在 `frameTcpPayload` 里另建字符串拼的，
所以它现在只是纯预留，理论上可以去掉。

### 栈上的 64 KB

```cpp
char extrabuf[65536];                       // 栈上 64 KB
vec[0].iov_base = begin() + writerIndex_;   // 第一块：Buffer 自己的可写区
vec[0].iov_len  = writableBytes();
vec[1].iov_base = extrabuf;                 // 第二块：栈
vec[1].iov_len  = sizeof(extrabuf);
const int iovcnt = (writableBytes() < sizeof(extrabuf)) ? 2 : 1;
readv(fd, vec, iovcnt);
```

这么写是为了一次系统调用尽量把内核缓冲读空，因为 ET 模式下必须排空。如果只读 Buffer 自己的
可写区，容量不够时就得再调一次 `readv`。

两个细节：`iovcnt` 是动态的，Buffer 空间本来就够大时没必要动栈；64 KB 放栈上也不危险，
默认线程栈有 8 MB，而 `readFd` 的调用深度很浅。但这个函数不能放进深递归或大栈帧里。

### gRPC 侧的生命周期

这里有三个坑。

第一个是 tag 必须先登记、后 `Finish()`：

```cpp
call->response_reader = stub_->PrepareAsyncAnalyzeFrame(&call->context, call->request, &cq_);
call->response_reader->StartCall();

void* tag = (void*)call.get();
{ std::lock_guard<std::mutex> lock(mu_); active_calls_[tag] = call; }  // 先登记
call->response_reader->Finish(&call->reply, &call->status, tag);        // 后 Finish
```

顺序反了，CQ 可能先送回一个表里还没有的 tag，也就是幽灵回调。

第二个是 `FrameRequest` 必须和 `context`、`reply` 同生命周期。它原来写在
`AnalyzeFrameAsync` 的栈上：

```cpp
vision::FrameRequest request;                    // 栈上
request.set_image_data(std::move(image_data));
call->response_reader = stub_->PrepareAsyncAnalyzeFrame(&call->context, request, &cq_);
// 函数返回，request 析构，而 gRPC 可能还没把它的字节发给对端
```

它当时能跑，只因为「序列化恰好同步完成」这一实现细节。现在它是 `AsyncClientCall` 的成员，
和 `context`、`reply` 一起活着：

```cpp
struct AsyncClientCall {
    FrameRequest  request;    // 与 context、reply 同生命周期
    FrameResponse reply;
    ClientContext context;
    Status        status;
    ...
};
```

第三个是失败和超时路径也必须在途额度归还。错误分支里同样要 `--in_flight_requests_`。
因为 `active_calls_` 里那个 `shared_ptr` 被 erase 了，而回投的闭包持有弱引用，两条路径都是干净的。

额度是一种逻辑资源，不是内存。它泄漏了不会报错，只会让这个连接永远回 `OVERLOADED`，
从过载保护退化成连接死亡。这是最难查的一类 bug，实验三会演示。

### 在途额度

```cpp
static constexpr size_t kMaxInFlightRequests = 2;

// 借
if (in_flight_requests_ >= kMaxInFlightRequests) { 回 OVERLOADED; return; }
++in_flight_requests_;

// 还，在 EventLoop 线程，成功、失败、超时三条路都汇到这里
loop->runInLoop([weakSelf, json]{
    if (auto self = weakSelf.lock()) {
        if (self->in_flight_requests_ > 0) --self->in_flight_requests_;
        self->sendInLoop(...);
    }
});
```

那句 `if (> 0)` 是防御性的。即使某天出现重复回调，计数也不会下溢到 `size_t` 的最大值，
那会导致永远 `OVERLOADED`。

### 一帧被拷贝几次

| 次数 | 拷贝 | 位置 | 能否避免 |
| --- | --- | --- | --- |
| 1 | 内核到用户态 | `readv` | 不可避免，但一次读得多 |
| 2 | `extrabuf` 到 Buffer | 只在溢出时发生 | 部分可避免 |
| 3 | Buffer 到 `std::string` | `retrieveAsString` | 可以改成视图，但 protobuf 要 `string` |
| 4 | `std::string` 到 protobuf | `set_image_data(std::move(...))` | 已经是移动 |
| 5 | protobuf 到 gRPC 发送缓冲 | gRPC 内部序列化 | 不可避免 |
| 6 | 响应 JSON 字符串 | `ostringstream` | 可接受，很小 |
| 7 | JSON 到 TCP payload | `frameTcpPayload` | 可以优化，比如预分配 |

真正的大拷贝是第二、三、五次，其中第三和第七是可优化点。但先测再优化，
这个项目已经验证过瓶颈不在网关侧。

### 回调里捕获什么

```cpp
FrameContextPtr          ctx_copy  = call->ctx;     // FrameContext 用强引用
std::weak_ptr<Connection> conn_copy = call->conn;   // Connection 用弱引用

threadpool->add([ctx_copy, conn_copy]() {
    ...
    if (auto conn = conn_copy.lock()) {             // 用之前先 lock
        conn->completeAnalysis(...);
    }
});
```

两种引用策略不一样，是因为两个对象的角色不同。`FrameContext` 是这一次请求自带的数据，
没有别人持有它，必须用强引用，否则回调时早就没了。`Connection` 是长生命周期的外部对象，
可能在等推理结果期间就断开了，必须用弱引用，否则连接本该销毁却被一个排队中的任务拖着，形成泄漏。

### 没有做的事

| 没做 | 为什么现在可以不做 |
| --- | --- |
| 内存池或对象池 | 每帧一次 `make_shared<FrameContext>`，相对二十毫秒的推理可以忽略 |
| 零拷贝传帧 | 同上，而且 Python 侧反序列化本来就要一份 |
| Buffer 收缩 | 稳态下可读区归零，搬移复用同一块，容量稳定 |
| 用 `unique_ptr` 管 `Acceptor` 和 `ThreadPool` | 应该改，见「如果重做」，目前的析构顺序是手工排对的 |
| 动态扩容 epoll 事件数组 | 固定 1024，只验证过单连接，够用 |

## 架构与取舍

### 为什么是单 Reactor

并发模型有四个常见选择，我们选了单 Reactor 加线程池：

| 方案 | 优点 | 为什么没选 |
| --- | --- | --- |
| 单 Reactor 加线程池 | 状态简单，连接的所有可变状态只有一个线程碰，好调试 | 单个 Reactor 是天花板，本项目的瓶颈在推理不在网关 |
| 多 Reactor | 能吃多核，连接可以分摊 | 需要跨 Reactor 投递和连接迁移，对学习项目是纯增复杂度 |
| 一连接一线程 | 代码最直白 | 每连接一个 8 MB 栈，上下文切换到爆，基本等于没设计 |
| 协程 | 写起来像同步 | 需要 C++20，而且会掩盖线程归属问题，而那正是本项目要学的 |

选择的理由和项目目标有关。这个项目要把生命周期和线程归属这条线走通并验证，
单 Reactor 正好把这些问题是暴露出来的，必须自己处理跨线程投递、弱引用和生命周期；
另外三个方案要么增加无关复杂度，要么把问题藏起来。

### 逐个技术点的取舍

**协议与缓冲。** 我们用 epoll 的边缘触发而不是水平触发，因为一次事件就能读空，减少唤醒次数，
代价是必须排空到 `EAGAIN`，而且读写事件都是边缘触发。读的时候用 `readv` 配一块栈上 64 KB 缓冲，
而不是单次 `read`，为的是一次系统调用读得更多，代价是栈上多占 64 KB、分支变多。
Buffer 用双游标而不是单游标，读的时候不搬数据，扩容前先做内部搬移，代价是游标不变式要自己维护。
另外留了八字节预留头，如前所述它现在只是纯预留。

**跨线程。** 我们不让 Worker 直接改连接状态，而是用 `eventfd` 加 `queueInLoop` 把闭包投回 Reactor。
备选方案是给 Buffer 加锁，但那保护不了整套跨对象状态机。代价是多一次唤醒，还要管闭包的生命周期。
`Channel::tie` 存的是 `weak_ptr` 而不是 `shared_ptr`，这样既不会 use-after-free 也不会泄漏，
代价是回调里必须先 `lock()` 判空。

**异步 gRPC。** 我们选异步存根而不是同步调用，发起后立刻返回，Reactor 不会被推理阻塞，
代价是 tag 表、生命周期和幽灵回调都要自己管。tag 必须先登记后 `Finish()`，代价是需要一把互斥量。
请求体放在 `AsyncClientCall` 里而不是栈上，因为异步 API 要求它活到调用结束，代价是结构体变大。
结果处理放在线程池而不是 CQ 线程，因为 CQ 线程不能被 JSON 序列化卡住，代价是多一次线程切换。

**背压与超时。** 每连接在途上限取 2，而不是无上限或排队，因为实时场景里延迟比吞吐重要，
丢一帧只是一个结果缺失，代价是高负载时会丢帧，这是有意为之。
每个 RPC 设两秒截止，因为不设的话推理侧挂住会永久占用额度，代价是慢推理会被误杀。
这里的推理是十几到二十毫秒，两秒很宽松。

**协议与计时。** 用四字节长度前缀而不是分隔符，因为二进制安全且拆包是 O(1)，代价是要做长度校验。
响应用手写 JSON 而不是 protobuf 二进制，便于调试且没有 schema 变更压力，
代价是浮点精度未控制、转义要手写。TraceID 用全局原子计数器，全链路一个号便于对日志，
代价是跨重启不唯一，够用。

### 三处反直觉的选择

有三个决定看起来可以更简单，但那样会出错，它们最值得讲。

**拆包不放进线程池。** 直觉上耗时操作都该丢线程池，但 `business()` 要读写 `inputBuffer`，
而 `handleReadEvent` 也在同一线程读写它。丢进线程池就必须给 Buffer 加锁，而且加锁仍然不够，
因为「读游标的一致性」和「整帧是否完整」是两件事。所以协议解析必须和 socket 读取同线程，
线程池只接没有共享状态的活，也就是 JSON 和日志。

**跨线程不用互斥量，用投递。** 只给 `outputBuffer` 加一把锁是不够的，它保护不了 `state_`、
`Channel::events`、`epoll_ctl` 以及析构顺序这一整套一致性。`02-设计决策.md` 里有完整的竞态时序。

**没写完不重试，直接转 `outputBuffer`。** `write()` 返回部分写时，看起来再写一次就行了，
但在非阻塞 fd 上重试会变成死循环，内核缓冲满了会一直返回 `EAGAIN`。正确做法是登记 `EPOLLOUT`，
让 epoll 来告诉我们可以写了。

### 如果重做会改的地方

| 问题 | 应该怎么改 |
| --- | --- |
| `handleWriteEvent` 和 `sendInLoop` 的部分写分支里有同步日志 | 删掉或改成异步日志。这和当年 929 微秒那次同源，都是 `std::endl` 每次 flush。正常单帧走不到这个分支，所以没体现在延迟数字里，但它确实在热路径上 |
| `Acceptor` 和 `ThreadPool` 用裸指针 | 换成 `unique_ptr`。现在的析构顺序是手工排对的，靠注释维持 |
| `Epoll::events` 固定 1024 | 改成可配或按需扩容 |
| 每帧一次 `make_shared<FrameContext>` | 帧率上去之后可以池化复用 |
| 没有优雅停机 | 加信号处理，先停 Acceptor，再取消在途 RPC、停 CQ、停线程池、释放连接。收益是 `Server::~Server()` 的顺序才能被真正执行和验证 |

## 小结

- 系统分两侧：网关侧是 C++ 程序，推理侧是 Python 程序，两者可以跨机器。
- 网关侧只有一个 Reactor 线程，所有连接的读写、拆包和发送都归它；其他线程要动连接必须回投。
- `Connection` 的强引用只有一处，就是 `Server::conns`，其余全是弱引用。
- `gateway_us` 只统计网关自己那三段，不含 gRPC 往返和推理。
- 在途上限和截止时间分别防的是堆积和额度泄漏。
