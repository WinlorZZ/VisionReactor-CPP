# 开始项目

这篇文档带我们从零把项目跑起来，最后发一张图片并拿到一段检测结果。
整个过程大约十五分钟，不包括下载依赖的时间。

文中每条命令都在这台机器上验证过，输出也是实际粘贴的。结果和文中不一样时先看[常见问题](#常见问题)。

## 先分清两侧

这个系统由两侧组成。它们在各自的进程里跑，不要求在同一台机器上。

| | 网关侧 | 推理侧 |
| --- | --- | --- |
| 是什么 | 本仓库编译出来的 C++ 程序 `server` | Python 程序 `Pserver.py` 或 `dummy_server.py` |
| 跑在哪 | 必须是 Linux 或 WSL，它依赖 `epoll` | 有 Python 就行；可以在 WSL 里，也可以在 Windows 上用 GPU——本机的 Windows 侧或另一台机器 |
| 做什么 | 收帧、拆包、转发、逐帧计时、把结果发回 | 解码图像、跑模型、报告自己的推理耗时 |
| 之间怎么连 | —— | gRPC，默认端口 50051 |

本文按侧分节，**一节里只有这一侧的命令**。准备工作要开三个终端：

| 终端 | 属于哪一侧 | 后面在哪一节 |
| --- | --- | --- |
| 终端 1 | 网关侧（Linux 或 WSL） | 「网关侧：编译与启动」 |
| 终端 2 | 推理侧（WSL，或 Windows——本机或另一台机器） | 「推理侧：环境与启动」 |
| 终端 3 | 客户端（跟网关同一台机器） | 「客户端：发一帧」 |

分清两侧之后，下面这些说法才不会混：`parse_us`、`queue_to_grpc_us`、`postprocess_us` 和
`gateway_us` 都是网关侧的；`infer_us` 是推理侧自报的，网关只是把它转述出来；
`total_us` 是端到端的，跨了两侧。

## 选择版本

仓库有两个分支，代码和文档都不一样。

`slim` 分支只保留 TCP 核心链路，生产代码 1920 行。`main` 是完整版，多出 WebSocket 直连、
H.264 解复用和浏览器演示，生产代码 2440 行，另有 66 个文件。

这篇文档以 `slim` 为准。两个分支在不少地方不同（构建命令、依赖、测试套件数），
遇到差异时会单独说明。

## 获取代码

两侧用的是同一份仓库，所以克隆一次就够。在终端 1 里执行：

```bash
git clone --branch slim https://github.com/WinlorZZ/VisionReactor-CPP.git ~/slim-run
cd ~/slim-run
```

机器上已经有 `~/slim-run` 时直接进去即可。没有网络时，可以从本机已有的仓库克隆，内容相同：

```bash
git clone --branch slim /mnt/f/Project/study_project/Network ~/slim-run
```

要完整版就把分支和目录换掉：

```bash
git clone https://github.com/WinlorZZ/VisionReactor-CPP.git ~/Network
```

确认一下拉到的东西：

```bash
git rev-parse --abbrev-ref HEAD   # slim 分支应输出 slim
git ls-files | wc -l              # slim 是 55，完整版是 66
ls docs/                          # slim 有 00 到 05 与 README.md
```

## 网关侧：编译与启动

以下命令全部在终端 1 里执行，这一节结束之前不需要切到别的终端。

### 安装系统依赖

```bash
sudo apt install -y build-essential cmake \
  libgrpc++-dev protobuf-compiler-grpc libprotobuf-dev protobuf-compiler
```

`slim` 只需要 gRPC、Protobuf 和 pthread。完整版的 `CMakeLists.txt` 里还有
`find_package(OpenSSL REQUIRED)` 和 `find_package(OpenCV REQUIRED)`，所以要再装两个包：

```bash
sudo apt install -y libssl-dev libopencv-dev
```

### 解决 googletest

编译测试需要 googletest，这一步最容易卡住。

`slim` 的 `CMakeLists.txt` 会按下面的顺序找它。装好 `libgtest-dev` 最省事，之后完全离线：

```bash
sudo apt install libgtest-dev
```

不想装系统包、但手头有 googletest 源码时，可以显式指定：

```bash
make release GTEST_SRC=/path/to/googletest-src
```

两样都没有时，CMake 会从 GitHub 下载，这需要网络。

注意，**CMake 不读 git 的代理配置**。它下载 GTest 用的是 libcurl，只看 `https_proxy`
和 `http_proxy` 环境变量。所以会出现 git 能克隆、CMake 却失败的情况，配置阶段卡大约 86 秒后
报 `Could not resolve host: github.com`。有代理时这样写：

```bash
export https_proxy=http://<代理地址>:<端口>
export http_proxy=$https_proxy
make release
```

另外，**WSL 下 CMake 可能找到 Windows 版的 GTest**。WSL 会继承 Windows 的 `PATH`，
于是有可能选中 `/mnt/d/miniconda3/Library/lib/cmake/GTest` 这样的路径。那是 MSVC 编译的库，
链接时会报出一堆 `??_R4...` 未定义引用。仓库已经拒绝 `/mnt/<盘>/` 下的 GTest 并给出提示，
按提示装 `libgtest-dev` 即可。

完整版没有 `find_package(GTest)`，只走 `FetchContent`，所以上面第一条对它不成立。
它要么联网下载，要么自己调 cmake：

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release \
  -DFETCHCONTENT_SOURCE_DIR_GOOGLETEST=/path/to/googletest-src
```

### 编译并跑测试

```bash
make release
```

配置阶段会打印一行，说明 GTest 用的是哪个来源：

```text
-- GTest: 使用系统安装的 googletest /usr/lib/x86_64-linux-gnu/cmake/GTest（离线）
```

编译结束不应有 error，16 核机器上大约 45 秒。产物在 `build-release/server`。
完整版没有 `release` 目标，用 `make build`，产物在 `build/server`。

跑单元测试：

```bash
ctest --test-dir build-release
```

实际输出：

```text
    Start 1: buffer_test
1/5 Test #1: buffer_test ......................   Passed    0.01 sec
    Start 2: thread_pool_test
2/5 Test #2: thread_pool_test .................   Passed    0.53 sec
    Start 3: connection_test
3/5 Test #3: connection_test ..................   Passed    0.47 sec
    Start 4: event_loop_test
4/5 Test #4: event_loop_test ..................   Passed    0.01 sec
    Start 5: response_serializer_test
5/5 Test #5: response_serializer_test .........   Passed    0.01 sec

100% tests passed, 0 tests failed out of 5
```

完整版多一个 `h264_demuxer_test`，共 6 个。

### 启动网关

推理节点的地址要填在命令行上。按推理侧的位置分三种填法：

```bash
# 1) 推理侧和网关在同一台机器上（路径 A）
./build-release/server 127.0.0.1:50051

# 2) 推理侧在本机的 Windows 侧（WSL 连 Windows 宿主）
./build-release/server $(ip route | awk '/^default/{print $3}'):50051

# 3) 推理侧在另一台机器上
./build-release/server 192.168.1.50:50051
```

第 2 种那个地址是 WSL 的 vEthernet 网关，也就是 Windows 宿主，本机实测是 `172.18.112.1`。
它只在同一台物理机上有意义。

第 3 种要填**那台机器的局域网地址**，在推理侧那台机器上查：

```powershell
ipconfig | Select-String 'IPv4'
```

并且那台机器要放行 `50051` 入站，否则连不通（见[常见问题](#常见问题)）。

这里只用了地址，所以**推理节点还没启动也没关系**，gRPC 连接要到第一帧发出去时才用得上。

注意，**网关启动后什么都不打印**。它没有「监听于……」这样的横幅，构造完就直接进 `epoll_wait`，
只在有事件时才有输出。别以为它没起来。要确认它在监听可以这样看：

```bash
ss -ltnp | grep 8888
```

这个终端先留着别关，回到终端 2 去做推理侧。

## 推理侧：环境与启动

推理侧要做三件事：建一个 Python 环境、装依赖、把节点跑起来。
先决定它跑在哪，两选一，**选定之后只看自己那条路径的命令**。

| 路径 | 什么时候选 | 需要 GPU |
| --- | --- | --- |
| A：和网关同一台机器 | 只想验证链路，或者手头没有多余的机器 | 不需要 |
| B：Windows + GPU | 要跑真实的 YOLOv8，借那边的显卡。可以是本机的 Windows 侧，也可以是另一台机器 | 需要 |

### 路径 A：和网关同一台机器

在终端 2 里执行，所有命令都是 Linux 或 WSL 的。

先建环境：

```bash
cd ~/slim-run
/usr/bin/python3 -m venv .venv
```

这里写的是 `/usr/bin/python3` 而不是 `python3`。如果 shell 里激活了 conda，`python3`
指向的是 conda 的 Python，建出来的 venv 会基于 conda 那个版本。两种都能用，
写全路径是为了和本文的环境一致。想确认现有 venv 基于谁，可以看它的 `pyvenv.cfg`：

```bash
grep home .venv/pyvenv.cfg     # /usr/bin 是系统 Python，~/miniconda3/... 是 conda
```

用 conda 也可以，但注意不要装在 `base` 里：

```bash
conda create -n vision python=3.10 -y
conda activate vision
```

把解释器记到两个变量里，后面都用它们：

```bash
PY=$PWD/.venv/bin/python
PIP=$PWD/.venv/bin/pip

# 用 conda 的话就是
# PY=python
# PIP=pip

$PY --version
```

装依赖。模拟节点不做推理，只要三个包，大约 11 MB：

```bash
$PIP install -q grpcio grpcio-tools protobuf
```

需要代理时 pip 看的也是环境变量：

```bash
export https_proxy=http://<代理地址>:<端口>
export http_proxy=$https_proxy
```

装完检查一下，然后启动节点：

```bash
$PY -c "import grpc, grpc_tools; print('grpcio OK')"

cd python_ai
$PY -u dummy_server.py --port 50051 --latency-ms 20 --boxes 2
```

输出的样子：

```text
[Proto JIT] 正在编译契约: /home/equinn/slim-run/proto/game_ai.proto
[Proto JIT] 契约编译完毕
[Dummy AI] gRPC 服务已启动: 0.0.0.0:50051 (模拟推理 20.0ms, 返回 2 个框)
```

注意必须**在 `python_ai` 目录下运行**，而且**要加 `-u`**。不加 `-u` 时 Python 的输出会被缓冲，
看起来像卡住了或者没启动。

这个终端也留着别关。

### 路径 B：在 Windows 上跑真实模型

这一节的命令全部在 Windows 的 PowerShell 里执行，本机的 Windows 侧或另一台机器都行，
不要拿到 WSL 里去跑。

**推荐用 Windows Terminal 的 PowerShell 标签页，别用传统控制台。** 传统控制台开着快速编辑模式，
用鼠标选中文本就会暂停进程输出，这种长跑的 server 很容易被误判成卡死；Windows Terminal
没有这个问题，而且制表符和中文不会错位、回滚缓冲也留得住启动日志。

推理侧的脚本要读仓库里的 `proto/game_ai.proto`，所以那台机器上也要有一份代码：

```powershell
git clone --branch slim https://github.com/WinlorZZ/VisionReactor-CPP.git F:\slim-run
cd F:\slim-run
```

如果那台机器上已经有这份代码，直接进它所在的目录即可。

接着准备 Python 环境。机器上已经有装好 torch 和 ultralytics 的环境时直接用它，比如：

```powershell
conda activate game
```

没有的话建一个，并装齐依赖。这一步会连带拉 torch 和一堆 CUDA 运行库，大约 2 到 3 GB：

```powershell
conda create -n vision python=3.10 -y
conda activate vision
pip install -q ultralytics grpcio grpcio-tools protobuf
```

实测这一步会装 57 个包，包括 `torch`（主文件 529 MB）、`torchvision`、`opencv-python`、
`triton`，以及 16 个 `nvidia-*` 库。装之前可以先看看清单：

```powershell
pip install --dry-run ultralytics | Select-Object -Last 20
```

装完检查一下：

```powershell
python -c "import grpc, grpc_tools, torch, ultralytics; print('OK', torch.cuda.is_available())"
```

最后启动节点。**必须先切到 `python_ai` 目录**，`Pserver.py` 里 `YOLO('yolov8n.pt')`
用的是相对路径。权重文件不入库，首次运行会自动下载（约 6 MB，需要网络）：

```powershell
cd F:\slim-run\python_ai
python -u Pserver.py
```

输出的样子：

```text
[Proto JIT] 检查契约文件: F:\slim-run\proto\game_ai.proto
[Proto JIT] 正在动态编译 gRPC 契约...
[Proto JIT] 契约编译完毕！
===================================
[GPU Check] PyTorch CUDA 可用状态: True
[GPU Check] 识别到显卡: NVIDIA GeForce RTX 4070 Ti SUPER
===================================
[AI Engine] Loading YOLO model...
[AI Engine] Model loaded successfully.
[AI Engine] gRPC Server is running on port 50051...
```

节点默认监听 `0.0.0.0:50051`，所以 WSL 里的网关连得过来。连不上时看[常见问题](#常见问题)最后两条。

这个 PowerShell 窗口也留着别关。

## 客户端：发一帧

回到网关那台机器，开终端 3：

```bash
cd ~/slim-run
PY=$PWD/.venv/bin/python      # 如果第三节用的 conda，这里换成 python
$PY tools/image_client.py --image <一张 JPEG>
```

返回的 JSON：

```json
{
  "frame_id": 1,
  "ok": true,
  "error": "",
  "timing": {
    "total_us": 32093,
    "gateway_us": 78,
    "parse_us": 21,
    "queue_to_grpc_us": 4,
    "grpc_round_trip_us": 32014,
    "grpc_transport_us": 11868,
    "infer_us": 20146,
    "postprocess_us": 53
  },
  "detections": [
    { "class": "person", "confidence": 0.91, "x": 640, "y": 420, "w": 180, "h": 420 },
    { "class": "person", "confidence": 0.78, "x": 300, "y": 380, "w": 120, "h": 260 }
  ]
}
```

走路径 A 时，`detections` 是模拟节点返回的假框。走路径 B 时它返回模型真正检出的目标，
比如下面这样，这与直接用 YOLO 跑同一张图的坐标完全一致：

```json
"detections": [
  { "class": "tie",    "confidence": 0.913, "x": 331.451, "y": 846.36,  "w": 121.868, "h": 180.602 },
  { "class": "person", "confidence": 0.889, "x": 344.024, "y": 507.622, "w": 687.245, "h": 851.732 }
]
```

终端 1 （也就是在wsl里第一次开的那个）里网关会同时打印逐帧探针：

```text
new client fd 12 IP: 127.0.0.1 Port: 35326
[Worker] Frame 1 boxes=2 infer=20.134ms
[Latency CT Scan] Frame: 1 | Total: 32.01 ms
  ├─ T1 (TCP Parse)   :   0.02 ms
  ├─ T2 (C++ -> gRPC) :   0.00 ms
  ├─ IPC (gRPC Trans) :  11.78 ms  <-- 跨语言开销
  ├─ T3 (Python YOLO) :  20.13 ms  <-- AI 纯算力开销
  └─ T4 (gRPC -> C++) :   0.07 ms
  --------------------------------------------------
[Connection] 收到 FIN，准备断开...
[Server] 已从 Map 中移除 fd 12，Server 对此连接的所有权已解除。
```

首帧的数字会偏大。上面这次 `grpc_transport_us` 是 11868 微秒，因为首帧包含建立 gRPC 通道的开销。
连续发几帧之后它会降到约 1.5 毫秒，看性能请看稳态。

## 读懂返回的 JSON

`detections` 里每一项是一个检测框：`class` 是类别名，`confidence` 是置信度，
`x` 和 `y` 是中心点坐标，`w` 和 `h` 是宽高。

`timing` 里有四个是直接测出来的：

| 字段 | 含义 |
| --- | --- |
| `parse_us` | 包头首次可见到拆出一个完整帧。半包时这段包含等待时间 |
| `queue_to_grpc_us` | 拆完帧到发起 gRPC |
| `infer_us` | 推理服务自报的耗时，包含它自己的解码 |
| `postprocess_us` | 收到回执到结果处理完、准备回发 |

其余三个是算出来的：

```text
grpc_round_trip_us = t_grpc_recv - t_grpc_sent
grpc_transport_us  = grpc_round_trip_us - infer_us      差值估计，含排队与序列化
gateway_us         = parse_us + queue_to_grpc_us + postprocess_us
```

`gateway_us` 刻意不含 gRPC 往返和推理，所以「网关侧只有 70 微秒」这句话才站得住。
判断一次调用是否正常，看三件事：`ok` 是 `true`；`gateway_us` 在几十到几百微秒之间；
`total_us` 主要被 `infer_us` 占掉。

## 这张 JSON 背后发生了什么

一帧从客户端到结果回来，经过以下几步。

1. epoll 报连接可读，`Buffer::readFd` 用 `readv` 读到 `EAGAIN`。
2. `business()` 在同一个线程里按四字节长度前缀拆出一整帧。
3. 检查每连接在途上限，超过两个就直接回 `OVERLOADED`。
4. 发起异步 gRPC，立刻返回，不阻塞事件循环。
5. 推理侧解码并推理。
6. CQ 线程收到回执，从 tag 表取出调用，把结果处理任务投给线程池。
7. 线程池序列化成 JSON，再回投事件循环，由事件循环线程写回客户端。

第二步、第四步和第七步是三处容易记错的地方，细节见 [05-带你过一遍.md](05-带你过一遍.md) 第 2 站。

## 常见问题

网关侧：

| 现象 | 原因与处理 |
| --- | --- |
| `make: *** No rule to make target 'release'` | 你在完整版目录里。`release` 目标只在 `slim` 分支上。完整版用 `make build`，产物在 `build/server` |
| 配置阶段卡约 86 秒后报 `Could not resolve host` | CMake 拉 GTest 需要网络，而且不读 git 的代理配置。设 `https_proxy`，或装 `libgtest-dev`，或传 `GTEST_SRC=` |
| 链接期出现大量 `??_R4...` 未定义引用 | CMake 选中了 `/mnt/<盘>/` 下 MSVC 版的 GTest。装 `libgtest-dev`，仓库会拒绝那个路径 |
| 完整版装了 `libgtest-dev` 仍要联网 | 完整版没有 `find_package(GTest)`。联网加 `https_proxy`，或自己调 cmake 传 `-DFETCHCONTENT_SOURCE_DIR_GOOGLETEST=` |
| 完整版报 `find_package(OpenCV)` 或 `find_package(OpenSSL)` 失败 | 完整版还要 `libssl-dev` 和 `libopencv-dev` |
| 网关什么都不打印 | 它本来就不打印。用 `ss -ltnp \| grep 8888` 确认在监听 |
| 返回 `code` 是 `RPC_FAILED` | 推理节点没启动，或者网关启动时填的地址不对 |
| 返回 `code` 是 `OVERLOADED` | 每连接在途请求超过两个。这是正常工作，让发送端放慢 |
| 返回 `code` 是 `TIMEOUT` | 单帧推理超过两秒的截止时间 |
| 客户端连接被拒 | 网关没启动，或者端口不对。默认是 `127.0.0.1:8888` |

推理侧：

| 现象 | 原因与处理 |
| --- | --- |
| Python 节点看起来没启动 | 输出被缓冲了，要加 `-u` |
| `Pserver.py` 报找不到模型 | 没在 `python_ai` 目录下运行；权重不入库，首次运行会自动下载，下载不了就手动放一份 `yolov8n.pt` 到 `python_ai/`，`YOLO('yolov8n.pt')` 用的是相对路径 |
| WSL 连不上本机 Windows 侧的推理节点 | 网关启动时该填 vEthernet 网关地址，本机实测是 `172.18.112.1`。另外防火墙或安全软件拦入站也会这样 |
| 连不上另一台机器上的推理节点 | 三件事：填的是**那台机器的局域网 IP**（不是 `172.18.112.1`，那个只在同一台物理机上有意义）、两台在同一网段、那台机器放行了 `50051` 入站 |
| Windows 上 `pip install` 卡住 | pip 也只看环境变量，需要代理时先设 `$env:HTTPS_PROXY` |

## 小结

- 系统分两侧：网关侧是 C++ 程序，必须在 Linux 或 WSL 上跑；推理侧是 Python 程序，可以同机也可以跨机器。
- `gateway_us` 只统计网关自己那三段，不含 gRPC 往返和推理。
- 模拟节点用来验证链路，不要拿它的数字代表真实 AI。
- 网关启动后没有输出是正常的。
