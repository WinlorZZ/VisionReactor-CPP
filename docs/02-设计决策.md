# 02 设计决策

每条都回答三个问题：选了什么 / 为什么 / 不这么做会出什么问题。
「会出什么问题」不是推测——要么能在代码里指出对应处理，要么实测过。

## 1. 单 Reactor + `epoll` ET，而不是一连接一线程

选了什么：一个 EventLoop 线程 + `epoll` 边缘触发 + 非阻塞 I/O。连接数增长时线程数不变。

为什么：一连接一线程在 C++ 里每连接要一个栈（默认 8 MB 虚拟内存）和一次上下文切换；
真正的瓶颈是"等 I/O"这件事，Reactor 把它收敛到一次 `epoll_wait`。

不这么做会怎样：ET 模式下如果只读一次就返回，内核缓冲区里剩下的数据不会再触发事件——
连接会静默卡死。所以 `handleReadEvent` 必须循环读到 `EAGAIN`，`Acceptor::acceptNewConnection`
必须循环 `accept` 到 `EAGAIN`。

代价（如实说）：只有单连接验证，没有多客户端压测，也没有多 Reactor。
详见 [03 文档](03-实测与边界.md)的边界表。

相关源码：[`EventLoop.cpp`](../src/EventLoop.cpp) · [`Epoll.cpp`](../src/Epoll.cpp) · [`Acceptor.cpp`](../src/Acceptor.cpp)

## 2. `readv` 双缓冲 + 双游标 Buffer

选了什么：`Buffer` 内部是 `vector<char>`，前置 8 字节预留头，两个游标（`readerIndex_` / `writerIndex_`）。
读的时候用 `readv` 一次投两块内存：Buffer 自己的可写区 + 栈上 64 KB `extrabuf`。

为什么：

- `iovcnt` 是动态决定的：`writableBytes() < 65536 ? 2 : 1`。Buffer 本身空间够大时不必用栈缓冲。
- 一次系统调用尽量读空内核缓冲，减少 ET 模式下的轮询次数。
- 双游标避免每次读取都搬数据；扩容前先做内部搬移（Tighten）——把可读数据平移到预留头之后，
  真实扩容只在连搬移都不够时才发生（`makeSpace`）。

不这么做会怎样：单游标实现要么每次读都搬数据，要么缓冲区无限膨胀；
没有预留头就没法在头部前置数据（长度前缀就需要往头里塞 4 字节）。

相关源码：[`Buffer.h`](../include/Buffer.h)（`readFd` / `makeSpace`）

## 3. 写侧排空到 `EAGAIN`，并维持「`outputBuffer` 非空 ⇔ `EPOLLOUT` 已注册」

选了什么：`sendInLoop` 先试直写；写不完就把剩余追加到 `outputBuffer` 并注册 `EPOLLOUT`。
`handleWriteEvent` 循环写到 `EAGAIN`，排空后立刻注销 `EPOLLOUT`。

为什么：这条不变式同时解决了两个问题——(a) 平时不监听 `EPOLLOUT`，避免无意义的唤醒；
(b) `sendInLoop` 靠它判断"该直写还是只追加"。

不这么做会怎样：

- 只写一次就返回：ET 下剩余的字节要等下一次"内核缓冲由满变可写"的新边缘才发出去，延迟不可控。
- 一直挂着 `EPOLLOUT`：每次 `epoll_ctl(MOD)` 都会重新触发一次就绪，产生额外唤醒。

非阻塞 `write` 的五种返回都要处理：`n == len`（完成）、`0 < n < len`（部分写，剩下的进 Buffer）、
`-1/EINTR`（重试）、`-1/EAGAIN`（保留 Buffer，等下次 `EPOLLOUT`）、其他 `errno`（关闭连接）。

相关源码：[`Connection.cpp`](../src/Connection.cpp) 的 `sendInLoop` / `handleWriteEvent`

## 4. 跨线程用 `eventfd` + `queueInLoop`，而不是给 Buffer 加锁

选了什么：线程归属。连接的 Buffer、Channel、epoll 状态只允许 EventLoop 线程改；
其他线程要动连接，就把闭包投递回 EventLoop 执行。

为什么：只给 `outputBuffer` 加一把 mutex 是不够的——它保护不了跨对象的完整状态机：
`Connection::state_`、`Channel::events`、`Channel::isadd`、`epoll_ctl`、以及 Connection 的析构时序。
这些对象之间需要一致，而不是各自线程安全。

不这么做会怎样（一个真实时序）：

```text
线程 A（Worker）：调 send()，看到 state_ == kConnected；
                  非阻塞 write() 返回 EAGAIN，准备把剩余数据追加到 outputBuffer —— 被切走

线程 B（EventLoop）：收到 FIN → handleClose() → state_ = kDisconnecting、关读事件
                    → 此时 outputBuffer 还是空的，于是认为没有待发数据
                    → state_ = kDisconnected，回调删除，从 Server::conns 移除
                    → 没有其他持有者，Connection/Channel 被析构、fd 被关闭

线程 A 恢复：即使加锁安全地把数据写进了 outputBuffer，
            随后 channel->enableWriting() 会去改一个可能已经析构的 Channel、对一个可能已被复用的 fd 调 epoll_ctl
```

结论：mutex 只能保护一块共享数据，保护不了跨多个对象的完整状态机。

相关源码：[`EventLoop.cpp`](../src/EventLoop.cpp) 的 `runInLoop` / `queueInLoop` / `doPendingFunctors`

## 5. `Channel::tie` 用 `weak_ptr`，不是 `shared_ptr`

选了什么：`Channel` 保存 `std::weak_ptr<void> tie_`；`Connection::connectEstablished()` 里调
`channel->tie(shared_from_this())`。`handleEvent()` 先 `tie_.lock()` 拿到局部 `guard`，再分发回调。

为什么：epoll 事件回调和连接销毁是两条独立的时间线。
断连时 `handleClose()` → 删除回调 → `Server::conns.erase()` 会把最后一个 `shared_ptr` 抹掉，
而此时我们正在 `Connection::handleReadEvent()` 里面执行。`guard` 让对象活到回调返回。

用 `weak_ptr` 而不是 `shared_ptr` 的理由：不改变引用计数。若 `Channel` 持有强引用，
`Server::conns.erase()` 之后就永远不会析构，连接泄漏。

不这么做会怎样：实测——去掉 `tie` 那行、用 ASan 构建、跑一个"发完就 RST 断开"的客户端，
会直接报 `heap-use-after-free`。注意 `connection_test` 里的 tie 用例不会失败（它没有真实 epoll 事件），
所以"单测通过"证明不了这件事。

相关源码：[`Channel.cpp`](../src/Channel.cpp) 的 `handleEvent` · [`Connection.cpp`](../src/Connection.cpp) 的 `connectEstablished`

## 6. 异步 gRPC：tag 先登记、后 `Finish()`

选了什么：用 `CompletionQueue` 而不是同步 stub。每次调用打包成 `AsyncClientCall`，
用它的地址当 tag；先把 tag 放进 `active_calls_`（加锁），再调 `Finish()`。

为什么：

- 推理是 10 毫秒级的，同步调用会把工作线程全占住；异步发起后线程立刻能去处理别的帧。
- 先登记后 `Finish`：否则 CQ 可能先送达一个表里还没有的 tag（幽灵回调）。
- `active_calls_` 存 `shared_ptr` 而不是裸指针：这样 CQ 线程取出它时对象一定还活着。
- 请求体 `FrameRequest` 也放在 `AsyncClientCall` 里，而不是放在 `AnalyzeFrameAsync` 的栈上——
  后者只靠"序列化恰好同步完成"这一 gRPC 实现细节才成立。

不这么做会怎样：tag 顺序反了会收到未知 tag；请求体放栈上则依赖未定义行为。
失败与超时都走同一条错误路径，所以在途额度一定会被归还。

相关源码：[`AsyncAIEngine.cpp`](../src/AsyncAIEngine.cpp) 的 `AnalyzeFrameAsync` / `AsyncCompleteRpc`

## 7. 每连接在途上限 2（背压）+ 每个 RPC 2 秒 deadline

选了什么：`kMaxInFlightRequests = 2`；超限立刻回 `OVERLOADED`，不排队、不丢旧帧。
每个 RPC 设 `kRpcDeadlineMs = 2000`；超时把 gRPC 状态映射成稳定的客户端错误码 `TIMEOUT`。

为什么：视频产帧速度必然快过推理。实时场景里延迟比吞吐重要——排队会让延迟线性增长，
而丢帧只是这一次没结果。上限 2 是"允许一点流水线，但不允许堆积"。

deadline 为什么必须有：没有它，AI 挂住而不报错时，`active_calls_` 里的条目和连接的在途额度
会被永久占用，该连接之后所有帧都被判 `OVERLOADED`——从"过载保护"退化成"连接死亡"。

不这么做会怎样：实测 burst 30 帧 → 2 帧受理、28 帧 `OVERLOADED`；
AI 推理 5 秒（> deadline）时 seq 3 帧全部 `TIMEOUT`（`{"TIMEOUT":3}`），
没有一帧变成 `OVERLOADED`——这恰好证明了额度被归还（若泄漏，第 2、3 帧必然 `OVERLOADED`）。

相关源码：[`Connection.cpp`](../src/Connection.cpp) 的 `submitImageInLoop` / `completeAnalysis`
· [`AsyncAIEngine.h`](../include/AsyncAIEngine.h) 的 `kRpcDeadlineMs`

## 8. 4 字节大端长度前缀，而不是分隔符

选了什么：请求和响应都是 `[4 字节大端 body 长度][body]`。长度必须 `> 0` 且 `<= 10 MiB`。

为什么：图像是二进制，任何"分隔符"都可能出现在数据里；长度前缀让拆包是 O(1) 判断。
大端是网络字节序约定（`htonl` / `ntohl`）。

不这么做会怎样：用分隔符就要转义，转义就有膨胀和边界 bug；长度非法时直接关闭连接，
避免把畸形数据当帧处理。半包时一行都不消费（`readerIndex_` 不动），靠下一轮从同一位置重看同一个头。

相关源码：[`Connection.cpp`](../src/Connection.cpp) 的 `business` · [`Protocol` 说明见 README](../README.md)

## 附：明确没有做的设计

| 没做 | 现状 |
| --- | --- |
| gRPC deadline 之外的超时/重试策略 | 只设 deadline，无重试、无熔断 |
| OutputBuffer 上限 | 只发不读的慢客户端能把它撑大 |
| 优雅停机 | 无 SIGINT/SIGTERM 处理，`loop()` 是死循环 |
| 多 Reactor / 多线程 EventLoop | 单 Reactor，未验证并发 |
| 结果协议换 protobuf binary | 手写 JSON，够用且便于调试 |
