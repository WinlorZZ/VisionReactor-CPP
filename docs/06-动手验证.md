# 动手验证

[00-开始项目](00-开始项目.md) 把链路跑通，这一篇接着做四个实验。每个实验只动一侧，改动很小，
但要观察到的东西都能直接回答一个问题。做完之后，「我知道」就变成「我验证过」。

## 开始之前

三个终端还是 00 里那三个：

| 终端 | 属于哪一侧 | 跑着什么 |
| --- | --- | --- |
| 终端 1 | 网关侧（Linux 或 WSL） | `build-release/server` |
| 终端 2 | 推理侧（WSL 或 Windows） | `dummy_server.py` |
| 终端 3 | 客户端（跟网关同一台机器） | 下面这些命令 |

脚本放在 `.verify/`，该目录不入库。三个终端里都先设好这两个变量，按自己机器的实际路径改：

```bash
VERIFY=/mnt/f/Project/study_project/Network/.verify
PY=$VERIFY/venv/bin/python
```

四个实验分别动哪一侧：

| 实验 | 动哪一侧 | 看什么 |
| --- | --- | --- |
| 一：半包 | 客户端（终端 3） | 终端 1 里的 `parse_us` |
| 二：去掉 tie | 网关侧（终端 1）改一行并重建，客户端（终端 3）断开 | 终端 1 里的 ASan 报告 |
| 三：让推理挂住 | 推理侧（终端 2）改参数，客户端（终端 3）发帧 | 客户端拿到的错误码 |
| 四：持续发帧 | 客户端（终端 3） | 吞吐与错误码分布 |

做实验时别让机器同时跑别的重活。推理耗时对这一点很敏感，同一张图、同一条链路，
换个时刻能从 15 毫秒变到 70 毫秒；那样观察到的数字就没法归因了。

## 实验一：半包

要观察的是网关侧怎么处理「长度头和包体分两次到达」。

客户端（终端 3）把一帧拆成两次 `send`，中间停半秒。这个脚本是纯标准库写的，不需要 grpcio：

```bash
$PY $VERIFY/half_packet_client.py --image <JPEG> --gap 0      # 对照组，一次发完
$PY $VERIFY/half_packet_client.py --image <JPEG> --gap 0.5    # 实验组，拆成两次
```

发完回终端 1 看网关探针：

```text
Frame: 1  ├─ T1 (TCP Parse) :   0.03 ms     ← 一次发完
Frame: 2  ├─ T1 (TCP Parse) : 509.21 ms     ← 拆成两次，等待被算进 T1
```

两组都是 `ok=true`：

| 组 | `parse_us` | 客户端总耗时 |
| --- | --- | --- |
| 对照组，`--gap 0` | 33 微秒 | 33.7 毫秒 |
| 实验组，`--gap 0.5` | 509210 微秒，约 509 毫秒 | 532.1 毫秒 |

`parse_us` 是从 `t_start` 到 `t_parsed`，而 `t_start` 在包头首次可见时打点。
如果半包时消费了游标，第二段数据到达时会被当成新包头解析，长度校验失败，连接会被关掉。
现在看到 509 毫秒而且帧正常完成，就说明 `FrameContext` 跨读保留、游标没动。

顺带这也说明了 `parse_us` 的口径边界：它包含半包等待时间。引用它的稳态值（约 4 微秒）时，
前提是整帧一次到达。

## 实验二：去掉 tie 会怎样

这个实验只改网关侧的一行代码，客户端只需要「发一帧之后立刻断开」。

网关侧（终端 1），先按 Ctrl-C 停掉原来的网关，把那行注释掉：

```cpp
// channel->tie( shared_from_this() );
```

然后在终端 1 里构建 ASan 版并启动。`GTEST_SRC` 指到本地 googletest 源码，这样不用联网：

```bash
cd ~/slim-run
make asan GTEST_SRC=.verify/gtest-src
ASAN_OPTIONS=detect_leaks=0 ./build-asan/server 127.0.0.1:50051
```

客户端（终端 3），发一帧之后用 RST 断开，不等回复：

```bash
$PY - <<'EOF'
import socket, struct
jpeg = open('<JPEG>', 'rb').read()
s = socket.create_connection(('127.0.0.1', 8888), 5)
s.sendall(struct.pack('>I', len(jpeg)) + jpeg)
s.setsockopt(socket.SOL_SOCKET, socket.SO_LINGER, struct.pack('ii', 1, 0))  # close 时发 RST
s.close()
EOF
```

终端 1 里立刻出现报告，位置就在读事件里：

```text
==16827==ERROR: AddressSanitizer: heap-use-after-free on address 0x50f000000cf0
    #0 Connection::handleReadEvent() src/Connection.cpp:86
freed by thread T0 here:
    #0 operator delete(void*, unsigned long)
    #1 std::_Sp_counted_ptr_inplace<Connection, std::allocator<void>, ...>::deallocate
SUMMARY: AddressSanitizer: heap-use-after-free src/Connection.cpp:86 in Connection::handleReadEvent()
```

释放栈里出现 `_Sp_counted_ptr_inplace<Connection>`，说明这个对象是被 `shared_ptr` 释放的：
`conns.erase()` 之后引用计数归零，而事件回调还在用它的成员。

而同一份构建下，单元测试**不会**失败。还是在终端 1：

```bash
ctest --test-dir build-asan -R connection_test
```

```text
100% tests passed, 0 tests failed out of 1
```

因为它没有真实的 epoll 事件，走不到「回调中途对象被删除」这条路径。
这是本仓库里「单测通过不等于正确」最直接的一个例子。

做完记得把那行改回来，重新构建。

## 实验三：让推理挂住

这个实验要动推理侧和客户端两侧，顺序是先让推理变慢、再连发。反面对照要改网关侧。

推理侧（终端 2），按 Ctrl-C 停掉原来的节点，把等待时间改大重启：

```bash
cd ~/slim-run/python_ai
$PY -u dummy_server.py --port 50051 --latency-ms 60000 --boxes 2
```

客户端（终端 3）连发十帧：

```bash
$PY $VERIFY/batch_client.py --image <JPEG> --frames 10 --mode burst
```

前两帧被受理，其余立刻回 `OVERLOADED`。两秒之后那两帧变成 `TIMEOUT`。
之后再发新帧会被受理，这是关键观察点，说明额度归还了。

反面对照在网关侧（终端 1）：把 `AsyncAIEngine::kRpcDeadlineMs` 从 2000 改成 60000，
重新构建再跑一遍。这时连接会一直回 `OVERLOADED`，永远不恢复——那才是没有 deadline 时的真实行为。

## 实验四：持续发帧

前三个实验都只发一两帧。要持续发，用 `batch_client.py`，它有两种模式：

| 模式 | 行为 | 用来看什么 |
| --- | --- | --- |
| `--mode seq` | 发一帧等一帧 | 稳态延迟分布与吞吐。在途数永远是 1，不会丢帧 |
| `--mode burst` | 一次连发 N 帧再收 | 背压：超过每连接在途上限的帧会被拒 |

客户端（终端 3）：

```bash
$PY $VERIFY/batch_client.py --image <JPEG> --frames 20 --mode seq
$PY $VERIFY/batch_client.py --image <JPEG> --frames 10 --mode burst
```

`seq` 模式会打出每个时间段的 min / 中位 / p95 / max 和 fps；`burst` 模式的 `error_codes`
里会出现 `OVERLOADED`。

注意，`seq` 模式**没有限速**，它拿到一帧回复就立刻发下一帧，所以实际帧率等于
「1 除以单帧往返时间」。想固定帧率或者无限持续，得自己在循环里加 `sleep`，
`batch_client.py` 没有这个参数。

还要注意，别拿它去压一个本来就很慢的推理节点。客户端的截止时间是 2 秒，一到点就放弃这一帧，
但**推理侧不会因此停下**，它还在算。如果推理比 2 秒慢，`seq` 模式每发一帧都会留下一个
「已被放弃但仍在计算」的请求，越堆越深，之后每一帧都超时。我们在这台机器上撞见过：
一边有别的任务占着 GPU，`seq 20` 帧的结果是 20 个 `TIMEOUT`，墙钟 40 秒。
遇到这种情况，重启推理节点就清空了。

## 三个错误码说明问题在哪一侧

| 错误码 | 含义 | 问题在哪一侧 |
| --- | --- | --- |
| `OVERLOADED` | 每连接在途请求已经到 2，网关当场拒绝，没有发出去 | 网关侧，而且它工作正常，只是发送端太快 |
| `TIMEOUT` | 网关已经把请求发出去，两秒内没等到回执 | 推理侧（或者它所在机器的负载） |
| `RPC_FAILED` | 请求根本没送到推理服务 | 推理节点没启动，或者网关启动时填的地址不对 |

调试时先看错误码落在哪一行，就能直接确定该查哪一侧，不用两头猜。

## 小结

- 半包不消费游标，代价是 `parse_us` 把等待时间也算进去。
- 去掉 `tie` 会真的 use-after-free，而且单元测试测不出来。
- 在途上限和截止时间分别防堆积和防额度泄漏；截止时间只保护网关，不会让推理侧停下。
- 持续发帧用 `seq` 模式，帧率由单帧往返时间决定；要固定帧率得自己加 sleep。
